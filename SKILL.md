# Agent Team Setup

Ты — **организатор**: готовишь структуру мульти-агентной работы в проекте.
Продуктовый код зон ты не пишешь — только протокол, доки и каркас. Цель —
чтобы несколько агентов (бекенд, фронтенд, мобильный, админка, QA — любой
набор) работали в одном репозитории, не ломая друг друга и не путаясь.

## Шаг 0. Разведка (до любых вопросов)

Осмотри репозиторий и ответь себе:

1. Есть ли уже `AGENTS.md` / протокол агентов? Есть ли код, какой?
2. Есть ли `HANDOFF.md` / README с состоянием проекта?
3. Что в git: ветка,_dirty ли дерево, есть ли remote?

От режима зависит всё:

- **Чистый проект** → полный сетап (шаги 1–5).
- **Протокол уже есть** → режим **синхронизации**: не перегенерируй артефакты
  поверх живого протокола — сверяй его с этим скиллом, предлагай только
  недостающие секции, изменения согласуй с владельцем.
- **Протокол есть, просят добавить зону** → режим **расширения**: новая
  строка в таблице ролей, новый mailbox, README зоны, обновление таблицы
  портов и гейтов.

## Шаг 1. Интервью с владельцем (обязательно, до первой строки)

Через AskUserQuestion, блоками. **Ничего не создавай, пока не получил
ответы.** Стек никогда не предполагается — он спрашивается.

Блок «состав команды» — какие зоны нужны в проекте:

- бекенд (API) · фронтенд (веб-клиент) · мобильный (iOS/Android) ·
  админ-панель · QA · свой набор. Предложи типовые пресеты (например
  «бекенд + фронтенд», «бекенд + админка + фронтенд», «бекенд + фронтенд +
  мобильный») и дай собрать свой список.

Блок «стек каждой зоны» — на каждую выбранную зону предложи **2–3 варианта
с плюсами/минусами и своей рекомендацией** (каталог —
`references/stack-options.md`; сверяй актуальность по официальной
документации). Ответ «пока не решил» допустим: тогда зона стартует по
правилу первой сессии (см. ниже).

Блок «порты и процесс»:

- dev-порт на каждую зону с запускаемым сервером (предложи схему: бекенду
  базовый, остальным — соседние; таблица фиксируется в AGENTS.md);
- язык документации и коммитов (предложи формат `feat(scope): …`);
- какие интеграции планируются (названия — только как план; изучать их
  агенты будут по официальной документации в момент задачи).

Блок «скиллы зон»: проверь, какие скиллы доступны в среде (список скиллов
сессии). Типовые потребности по ролям: бекенд — скилл безопасности API;
фронтенд/админка — дизайн-скилл + security-ревью; мобильный — скилл
мобильной разработки и безопасности. Чего не хватает — создай проектные
версии через skill-creator (шаг 3).

## Шаг 2. Генерация артефактов

Собери из `references/` (заполни все `{{PLACEHOLDER}}`):

1. **`AGENTS.md`** (корень) — по `agents-md-template.md`: таблица ролей
   (только выбранные), порядок входа в сессию, таблица скиллов и гейтов,
   dev-порты, почтовая дисциплина, правило «баг у соседа», правила качества.
2. **`HANDOFF.md`** (корень) — по `handoff-template.md`: состояние проекта
   по итогам разведки, архитектура, TODO.
3. **README каждой зоны** — по `zone-readme-template.md`: стек (выбранный
   или «фиксируется на первой сессии»), порт, скиллы, DoD.
4. **`docs/mailbox/to-<роль>.md`** на каждую роль — по
   `mailbox-template.md` (гвард «чей ящик» обязателен).
5. **`zones.yml` + pre-commit hook** — карта владения зонами и хук по
   `zones-doctor-template.md`; настройте `git config core.hooksPath`.
6. **`.gitignore`** — дополнить гвардами сессионных артефактов
   (`.zcode/plans/`, `.zcode/shots/`) и секретов, если их там нет.

## Шаг 3. Проектный скилл security-ревью

По `security-review-template.md` создай `<проект>/.zcode/skills/security-review/SKILL.md`
с чек-листом под выбранные стеки (backend API / web UI / mobile — только
применимые блоки) и впиши его в гейты соответствующих зон в AGENTS.md.
Если в среде уже есть подходящий user-скилл — проектная копия всё равно
надёжнее: она побеждает по приоритету и не зависит от окружения.

## Шаг 3b. Гейты владения зонами и целостности протокола

Два детерминированных барьера по `zones-doctor-template.md`:

1. **`zones.yml` + pre-commit hook** — карта владения (glob → роль),
   генерируется из таблицы ролей. Хук блокирует коммит, затрагивающий
   файлы чужой зоны (владелец зоны в явном allowlist). Правило «чужие
   каталоги не трогать» превращается из строки в AGENTS.md в
   проверяемый барьер — тот же скачок, что «доки ↔ код».
2. **Скрипт-доктор протокола** (`check_protocol.py`): все ящики на месте
   и с гвардом в шапке; каждый гейт из AGENTS.md реально существует
   (скрипт/команда запускается); таблица портов полная и без дублей;
   zones.yml покрывает все зоны; docs-sync-скрипт запускается зелёным.
   Организатор запускает доктора сразу после генерации — сгенерированный
   протокол обязан сам проходить собственные проверки.

Оба скрипта живут в репо (это код проекта) и правятся агентами зон как
обычный код.

## Шаг 3c. Конвенция чистого кода

Впиши в AGENTS.md секцию «Чистый код» (шаблон —
`clean-code-template.md`, заполни под выбранные стеки):

- **Без дубликатов**: перед написанием — поиск по зоне готового
  (сервисы/компоненты/утилиты); третья копия кода = вынести в общий
  модуль своей зоны; между зонами дубли запрещён — общее через контракт.
- **Без ошибок в производстве**: линтер/форматтер обязательны и входят в
  гейт зоны (не «по желанию»); статическая типизация, где стек даёт
  (TypeScript, mypy, Kotlin null-safety); обработка ошибок на границах
  (сеть, ввод, парсинг) — обязательные ветки, не «позже»; новая фича =
  новые проверки, включая негативные.
- **Безопасность по умолчанию**: валидация всего входа на границе
  (allowlist, не blacklist); минимум привилегий и минимум зависимостей
  (новая зависимость = обоснование + зафиксированная версия); секреты
  только в env вне git; PII и токены не в логах; security-ревью диффа
  перед коммитом (шаг 3).
- Формулировки в AGENTS.md — короткие и проверяемые: агент должен уметь
  ответить «да/нет» по каждому пункту, а не «старался».

## Шаг 4. Гейт «доки ↔ код» (если у проекта есть API/БД)

Если в проекте есть публичный API и/или схема БД — создай скрипт сверки
доков с кодом по `docs-sync-template.md` (алгоритм + пример адаптации),
положи в зону бекенда и впиши в её гейт: «изменил роутер/модель — зелёный
скрипт или работа не готова». Для стека без готового паттерна — минимум
чек-лист в README бекенда.

## Шаг 5. Верификация и коммит

- Чек-лист: AGENTS.md и HANDOFF.md на месте; таблица портов полная; на
  каждую роль есть mailbox с гвардом; README зон фиксируют стек и порты;
  security-review-скилл создан и упомянут в гейтах; `zones.yml` покрывает
  все зоны; `.gitignore` закрыт.
- Если в репо есть код — прогони заявленные гейты зон, чтобы стартовые
  инструкции не были ложью.
- **Запусти доктора протокола** (`zones-doctor-template.md`): свежий
  протокол обязан проходить собственные проверки; красный доктор = сетап
  не закончен.
- Заверши **локальным коммитом** (push не делать никогда без явного приказа
  владельца) и перечисли владельцу созданное + открытые вопросы.

## Шаг 6. Стартовые промпты владельцу

Выдай владельцу заготовки первого сообщения для каждого агента
(`references/role-prompts.md`), заполнив роль/путь/задачу: агент без
указания роли не знает, кто он; промпт маршрутизирует в протокол, а не
дублирует его.

## Правило граблей (зашифровать в шаблон README зоны)

В каждом README зоны есть append-only секция «Грабли»: наступил — добавь
строку (симптом → причина → как обойти). Секция существует для передачи
опыта между сессиями и не нарушает правило «доки без истории»: «доки —
текущее состояние» касается контрактов и правил, «грабли» — известные
ловушки; строка-грабля, потерявшая смысл (починена, неактуальна),
удаляется тем же агентом, который починил причину.

## Эскалация споров (зашифровать в AGENTS.md)

Шаги спора между агентами (контракт, приоритет, зона):

1. Письма в ящики друг друга с фактами (не с оценками).
2. Нет согласия за одну итерацию — оба ставят статус `NEEDS_CONTEXT`
   с пометкой «спор: <тема>» и привлекают владельца (в обеих записях).
3. **Владелец — единственный арбитр**; его решение фиксируется в доках
   (AGENTS.md/контракты) коммитом агента, который реализует, и ссылкой
   в обеих записях mailbox.
4. Молча делать по-своему при открытом споре запрещено — это ломает
   соседа хуже, чем сам конфликт.

## Правило первой сессии зоны (зашифровать в AGENTS.md)

Если стек зоны не зафиксирован в её README — агент зоны **до первой строки
кода** спрашивает владельца: 2–4 варианта стека с плюсами/минусами и своя
рекомендация. Выбор фиксируется в README зоны и с этого момента является
контрактом: менять стек — отдельная задача с согласования владельца.

## Принципы, которые нельзя нарушать при генерации

- **Ничего не выдумывать о проекте**: всё содержимое — из разведки и интервью.
- **Нейтральность**: шаблоны не содержат имен, доменов, портов и скиллов
  какого-либо другого проекта — только заполнители.
- **Интеграции**: состав определяет владелец; каждая изучается по
  официальной документации, не по памяти агента.
- **Доки = текущее состояние**: без исторических заметок «что удалили».
- **Секреты и сессионные артефакты** (планы, скриншоты, временные скрипты) —
  вне git.
- **Коммит обязателен**: агент завершает работу локальным коммитом; рабочее
  дерево не оставляется грязным.
